💉SQL injectionT30.04 · T30.05
What the attacker sends
Input with SQL syntax into a field, e.g. ' OR 1=1 --, when the app builds the query by gluing strings.
Why it works
The DB can't tell the app's SQL from the attacker's. ' ends the string, OR 1=1 is always true, -- comments out the rest → returns every row / login bypass.
The one fix
Parameterised queries (prepared statements). Query + value sent separately, so input is data, never code.
cur.execute( "… WHERE name = ?", (name,))
Trap: "input validation" / "escape by hand" are not the best answer — pick parameterised queries (or an ORM).
📜XSST30.02 · T30.03
What the attacker sends
A script the trusted site serves to a victim's browser. Stored (saved on server, hits all), Reflected (in a URL, bounced back), DOM (page's own JS).
Why it works
The browser can't tell the injected script from the site's own code, so it runs it → session theft, actions as the user, defacement.
The one fix
Encode / escape output for its context. Browser shows the script as text, runs nothing.
html.escape("<script>") # &lt;script&gt;
Trap: CSP + HttpOnly are extra layers, not the fix. HttpOnly = XSS cookie theft.
📮CSRFT30.06 · T30.07
What the attacker sends
A hidden request from a malicious page to a site the victim is logged in to. No script runs on the target.
Why it works
The browser attaches the session cookie automatically, so the forged request looks legitimate → unwanted actions (change password, transfer funds).
The one fix
Anti-CSRF token checked on every state-changing request. The evil page can't read it → rejected.
hmac.compare_digest( form.csrf, session.csrf)
Trap: SameSite backs it up (not the sole fix). XSS defeats every CSRF defence.
