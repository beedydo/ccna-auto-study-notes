URI
T16.02
 /restconf/data/<module>:<node>
Path follows the YANG tree (T14). Root found via /.well-known/host-meta. /data = datastore, /operations = RPCs.
https://10.10.20.48/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1/description?content=config
root + datastoremodule:container / leaflist=keyquery
1discover the rootGET /.well-known/host-meta → href='/restconf'
2RPC (save the config)POST /restconf/operations/ cisco-ia:save-config
!Trap: a / inside a key must be %2F: interface=GigabitEthernet1%2F0%2F1. Unencoded → wrong path (400/404).

T16.03 · T16.05
 GET · POST · PUT · PATCH · DELETE
HTTP methods map to NETCONF ops. Success is 200 (data), 201 (created) or 204 (done, no body). Errors carry ietf-restconf:errors with an error-tag.

HEADERS
T16.04
 application/yang-data+json
Accept = what I want back. Content-Type = what I send. Auth = HTTP Basic over HTTPS.
1JSONapplication/yang-data+json
3Basic authcurl -u user:pass · auth=AUTH
2XMLapplication/yang-data+xml
4no Accept on IOS XE → XML back
!Trap: plain application/json is not a RESTCONF type → 415 as Content-Type, 406 as Accept (RFC 8040 rule).

QUERY
PARAMS
T16.06
 ?content= · ?depth= · ?fields=
Trim a GET reply on the server side. Only for GET (and HEAD); anything unexpected → 400.
1config vs state?content=config nonconfig all
3pick leaves (; = and, () = inside)?fields=interface(name;enabled)
2limit nesting?depth=1 … 65535 · unbounded
!Trap: defaults: content=all, depth=unbounded. Oper counters = nonconfig.

NETCONF
vs
RESTCONF
T16.08
 same YANG, different transport
Both read and write the same YANG data. Pick by transport, encoding and whether you need candidate + commit.
NETCONF (T15)RESTCONF (T16)
TransportSSH 830HTTPS 443
EncodingXML onlyJSON or XML
OperationsRPCs: get-config edit-configHTTP methods on URIs
Datastoresrunning · candidate · startup, lock / commitone unified datastore, no lock, no commit
!Trap: "needs a candidate datastore / commit / lock" → NETCONF. "JSON over HTTPS with HTTP verbs" → RESTCONF.
