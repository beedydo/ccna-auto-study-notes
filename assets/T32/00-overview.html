The TDD loop: test first, then code, then clean

T32.01

🔴 RED

Write one failing test for the next requirement. Run it and see it fail. def test_enabled_is_bool(self): FAILED (failures=1, errors=1)
➜

🟢 GREEN

Write the minimum code that passes. Nothing extra. .text == "true" + enabled_names() Ran 8 tests · OK
➜

🔵 REFACTOR

Clean the code; tests unchanged and still green. def _text(intf, tag): still OK
⬅ back to RED
next requirement = next failing test
Benefits (1.3): 1clear requirements (test = spec) 2fewer regressions 3safe refactoring 4better, testable design 5living docs + fast CI feedback
!Trap: code first, tests after ≠ TDD. Refactor changes code, never behaviour or the tests. TDD doesn't remove integration tests or guarantee zero bugs.

Test types: scope decides the name

T32.02

🧩 Unit

one function/class in isolation; fakes replace network/DB. Fast, many.iflib.parse_interfaces()

🔗 Integration

components together (app + API).TestAgainstRealDevice

🌐 Functional / E2E

whole system vs requirements. Slow, few.workflow → VLAN on switch?

🔁 Regression

re-run old tests after every change so fixed bugs stay fixed.CI on each commit (T28)
!Trap: "no network, sample input, one function" → unit. "Real API reply parsed" → integration. Regression is a habit (re-running), not a scope.
