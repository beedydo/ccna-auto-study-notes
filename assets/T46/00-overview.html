Trap: order is branch → commit → push → PR → CI → review → fix → approve → merge. Review happens before merge; CI runs on every push and does not replace the human reviewer. Branch protection = "required reviews" + "required status checks".

🎯 Why review (the benefit questions) T46.01 · T46.05

1
Find defects + security issues early: cheaper before merge than in prod (PR #42: return x in the loop, verify=False)
2
Share knowledge: 2+ people know each change; fewer single points of knowledge (bus factor)
3
Consistent style + standards across the codebase (PEP 8, team checklist)
4
Mentoring + code quality: juniors learn; code health improves over time
Trap: "makes code run faster", "replaces testing" or "removes the need for CI" are never the benefit

🔧 What to look for: CI vs human T46.04

⚙️ Linters / CI catchstyle, unused import os, bare except, missing timeout=, verify=False
🧐 Humans catchlogic bugs, hard-coded password, missing tests, unclear names (chk, x), magic 100, design
1
Checklist: design · functionality · security · tests · naming · readability
2
Small, focused PRs (~100 lines ok, 1000 too big); one change per PR
Trap: style debates belong to the linter/formatter in CI, not to human reviewers

💬 Giving feedback T46.04

Blockingbug / security / missing test → Request changes Should fixtimeout, error handling: explain why Nit:polish; author may ignore
1
About the code, not the person: "this loop returns early", not "you broke it"
2
Specific + actionable: line, problem, why, suggested fix; praise good parts too
Trap: the reviewer points out the problem + why; the author owns the fix (new commit on the same branch, not a new PR)
